# 포트폴리오 검토

## Overview

기술이사 관점의 포트폴리오 기준. 전제 하나: **포트폴리오는 이력서가 통과한 뒤에야 열린다.**
그리고 끝까지 보지 않는다. 그래서 포트폴리오의 목적은 "다 보여주기"가 아니라
**면접에서 받고 싶은 질문을 유도하는 것**이다.

## When to Use

- GitHub / 블로그 / 개인 사이트를 정리할지 판단할 때
- 어떤 프로젝트를 넣고 뺄지 고를 때
- README·첫 페이지 작성
- 회사 프로젝트를 공개할 수 없는 상황
- 팀 프로젝트·클론 코딩·AI로 만든 프로젝트를 어떻게 다룰지

## 핵심 원칙 — 희소해야 가치가 있다

넣을수록 강해지지 않는다. **어필 항목을 하나 정하고 거기에 집중한다.**

- GitHub 어필은 **한두 개만**. 나머지는 정리하거나 비공개
- 프로젝트를 많이 넣으려 하지 않는다. 한 프로젝트를 깊게
- 직무와 관계없는 것은 뺀다

## 넣지 말아야 할 것

| 항목 | 이유 |
|---|---|
| 죽어 있는 블로그 | 링크가 곧 감점이 된다 |
| 단순 지식 정리만 있는 블로그 | 검색으로 나오는 내용은 나를 설명하지 않는다 |
| 무의미한 1일 1커밋 | 잔디는 성실함이 아니라 공백으로 읽힌다 |
| 문서 작업만 한 오픈소스 기여 | 기여의 성격이 드러난다 |
| 설명할 수 없는 기술 | 첫 질문에서 무너진다 |
| 클론 코딩을 경험처럼 포장 | 반드시 들킨다 |
| 동작하지 않는 프로젝트 | 배포 URL이 죽어 있으면 열지 않는다 |
| 기능 목록만 나열한 README | 판단이 없다 |
| 방치된 팀 프로젝트 | 내가 뭘 했는지 알 수 없다 |
| 프로젝트의 한계를 숨김 | 한계를 아는 것 자체가 평가 대상이다 |

## 첫 페이지 / README 계약

첫 페이지에서 다음이 순서대로 보여야 한다.

1. 이 프로젝트가 **무엇을 해결하는가** (한 줄)
2. **동작하는 증거** — 스크린샷·데모 URL·실행 명령
3. **왜 이렇게 설계했는가** — 검토한 대안과 기각 사유
4. **한계와 다음 단계** — 숨기지 않고 명시
5. 기능 목록은 그 뒤

기능 목록으로 시작하는 README는 "만들었다"만 말하고 "판단했다"를 말하지 않는다.

## 설계 원칙

- **질문이 나오게 설계한다.** 면접관이 물어봐 주길 바라는 지점을 눈에 띄게 둔다
- **기준과 신념을 넣는다.** 왜 이 구조를 택했는지가 곧 나의 판단력이다
- **생각의 흐름을 따라오게 한다.** 결과만이 아니라 과정과 실패도 기록한다
- **실무와 유사하게 만든다.** 장난감이 아니라 운영을 상정한 형태로
- **AI와 협업한 것을 보여준다.** 숨기지 말고, 맡긴 범위와 검증 방식을 드러낸다
- **신입은 가능성을, 경력은 판단력을** 보여준다
- 블로그는 꾸준히, **과정과 실패도** 쓴다. 링크드인도 운영한다
- 팀 프로젝트는 방치하지 말고 **내 기여 중심으로 재가공**한다
- 공개 전략을 정한다 — 무엇을 공개하고 무엇을 비공개로 둘지 의도적으로

## 검토자의 시선 (자가 점검)

- [ ] **언제 보는가** — 이력서 통과 후에야 열린다. 이력서가 먼저다
- [ ] **끝까지 보지 않는다** — 첫 페이지에 승부가 걸린다
- [ ] **프로젝트를 보는 시선** — 무엇을 판단했는가
- [ ] **블로그를 보는 시선** — 최근 글이 언제인가, 남의 지식인가 내 경험인가
- [ ] **GitHub을 보는 시선** — 핀 고정 저장소가 나를 대표하는가
- [ ] **희소성** — 항목을 늘려서 약해지지 않았는가
- [ ] **3분 안에 검토해 본다** — 3분 동안 무엇이 전달되는가

## 자주 나오는 질문

- **AI로 만든 프로젝트를 넣어도 되나** → 된다. 단 어디까지 AI가 했고 무엇을 검증했는지 밝힌다
- **회사 프로젝트를 공개할 수 없다** → 코드·수치를 옮기지 말고, **문제의 성격과 판단**만 재구성한다.
  기밀·미공개 운영 지표는 어떤 형태로도 옮기지 않는다
- **개인 웹사이트가 꼭 필요한가** → 필수는 아니다. 운영할 수 없으면 없는 편이 낫다
- **블로그를 지금 시작해도 되나** → 된다. 죽은 블로그보다 방금 시작해 살아 있는 블로그가 낫다
- **GitHub을 정리해야 하나** → 한두 개만 남기고 정리한다
- **이력서와 포트폴리오 차이** → 이력서는 "이 사람을 만나볼까", 포트폴리오는 "무엇을 물어볼까"

## 후속 — humanize-korean 윤문 (조건부)

이 스킬의 기본 산출물은 지적 코멘트다. 코멘트는 포트폴리오 본문이 아니므로 윤문하지 않는다.
**README·첫 페이지·블로그 글 문장을 실제로 써 주거나 고쳐 준 경우에만**
`humanize-korean:humanize-korean` 스킬을 호출한다.

| 상황 | 윤문 |
|---|---|
| 넣고 뺄 항목 판단, 체크리스트만 반환 | 하지 않는다 |
| README 상단 4단(문제/증거/설계 근거/한계) 문장을 작성 | 한다 |
| 블로그 글 초안을 써 줌 | 한다 |

- **입력**: 산문 단락만. 코드 블록, 실행 명령, 배지·링크 줄, 기능 목록 표는 제외한다
  (humanize가 문장으로 오인해 다듬으면 그대로 깨진다).
- **route_hint**: 글 하나면 `standard`, README + 블로그 글을 함께 넘기면 `heavy`.
  등급 B 이하면 `heavy` 로 1회 재실행하고 멈춘다.
- **윤문 후 확인**: 기술명·버전·URL이 그대로인가 / 한계 서술이 완곡해져 흐려지지 않았나.
  포트폴리오에서 한계 서술은 hedging이 아니라 평가 대상이므로, humanize가 이를
  "과도한 hedging"으로 보고 깎았다면 해당 문장은 되돌린다.
- humanize는 판단을 만들어내지 못한다. **기능 목록만 있는 README는 윤문해도
  기능 목록이다.** "왜 이렇게 설계했는가"는 위 계약으로 먼저 채운다.
