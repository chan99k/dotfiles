# PR 본문 구성

`SKILL.md` Step 4의 상세 규정. 길이 상한, 커밋 단위 섹션, 스크린샷 배치를 다룬다.

다이어그램은 [pr-diagram.md](pr-diagram.md)가 단독으로 규정한다 - 이 문서는 재정의하지 않는다.

## 1. 길이 상한

**산문 목표 1,500자, 상한 2,000자.** 아래는 세지 않는다.

| 제외 | 이유 |
|---|---|
| 코드블록 | 읽지 않고 훑는다 |
| mermaid | 렌더된 그림이 본체이고 소스는 안 읽힌다 |
| 표 (스크린샷 표의 캡션 포함) | 셀 단위로 스캔된다 |
| 이미지 | 글자가 아니다 |
| 체크리스트 | 템플릿 고정분 |

이들은 스캔되고 산문은 읽히므로 리뷰어가 치르는 비용이 다르다. bullet 목록과
소제목은 센다 - 목록은 결국 읽어야 하고, 표로 압축할 수 있는 것을 목록으로 늘어놓은
경우 그 비용이 드러나야 한다.

diff 크기와 연동하지 않는다. 실측에서 둘은 상관이 없었다 - 15줄 diff에 산문 1,900자 가까이가
정당한 PR(원인 사슬이 본문의 전부)이 있었고, 1,700줄 diff에 360자로 충분한 PR이 있었다.
본문 길이를 정하는 것은 변경량이 아니라 설명해야 할 인과의 깊이다.

| 구간 | 판정 |
|---|---|
| ~1,500자 | 목표 구간. 정상 |
| 1,500~2,000자 | 상한 부근. 아래 이동 규칙을 검토한다 |
| 2,000자 초과 | 이동 규칙을 적용한다 |
| 적용 후 2,200자 이내 | 통과. 더 깎지 않는다 |
| 적용 후에도 2,200자 초과 | PR 분할을 검토한다 |

**2,000자는 상한선이고 2,200자가 실제 게이트다.** 하드 게이트로 두면 이동 규칙을
다 적용한 뒤 남은 수십 자를 맞추려고 무의미한 절삭을 하게 된다. 예를 들어 "마이그레이션 SQL의
내용, 파일명, 적용 순서"를 "SQL 내용, 파일명, 순서"로 줄여 13자를 버는 조정은 리뷰어에게 아무
이득이 없다. 여유분은 그런 절삭을 하지 않기 위한 것이지 상한을 2,200으로 올린 것이 아니다.

### 초과분은 삭제가 아니라 이동한다

내용을 잘라내면 리뷰어가 승인에 필요한 근거를 잃는다. 옮길 곳을 먼저 찾는다.

| 내용 | 이동처 |
|---|---|
| 검증 절차, 실측 반복 횟수 | 표로 압축한다. 표는 글자수에 안 들어간다 |
| 설계 대안 비교, 기각 사유 | design doc 과 워크스루 문서를 쓰고 링크한다 |
| 커밋 하나에만 해당하는 구현 세부 | 그 커밋 메시지 body |
| 후속 작업 목록 | 이슈 트래커 |
| 시행착오 서사 | 버린다. 리뷰어에게 필요한 것은 최종 상태다 |

**표 압축이 가장 크게 듣는다.** 약 4,000자 본문을 2,000자로 깎은 사례에서 감소분의
절반이 표로 흡수됐다. "전/후/무엇이 문제였나", "대상/변경/비고", "무엇을 어떻게
측정해 무엇이 나왔나" - 이런 산문은 원래 표의 형태이고, 표로 옮기면 정보가 하나도
줄지 않는다. 반면 커밋 메시지로 옮긴 것은 0건이었다. 나머지는 같은 말을 반복하던
문장을 지운 것이다.

## 2. 커밋 단위 섹션

- **트리거**: 커밋이 여럿이고 **각 커밋이 독립적인 설명을 요구**할 때. 커밋 수만으로는
  트리거되지 않는다 - 하나의 설명으로 전부 덮이면 `Changes`를 나누지 않는다.
- **렌더**: `Changes` 아래 `###` 소제목.
- **계약**:

```
### N. {커밋 subject} {8자 해시}
```

소제목을 따로 짓지 않고 **커밋 subject를 그대로 쓴다.** subject가 이미 그 커밋의
한 줄 요약이므로 별도 요약을 붙이면 같은 말이 두 번 들어간다.

```
BAD   ### 1. DB 마이그레이션을 infrastructure 계층으로 이관 5a7689ee
GOOD  ### 1. chore: DB 마이그레이션을 infrastructure 계층으로 이관 5a7689ee
```

**해시는 백틱으로 감싸지 않는다.** GitHub는 본문 평문의 7자 이상 hex SHA를 해당 커밋
링크로 자동 변환하는데, 이 변환은 평문에만 적용되고 코드 스팬(`` ` ``) 안은 리터럴로
확정돼 링크가 붙지 않는다. 감싸는 순간 아래 "머지 후 역추적" 근거가 절반만 남는다.

**해시는 subject 뒤에 둔다.** 소제목을 세로로 훑을 때 먼저 걸려야 하는 것은 8자 hex가
아니라 subject다. 해시는 그 줄의 식별자가 아니라 참조 링크다.

**해시만 적지 않는다.** PR이 열려 있는 동안 해시는 가변이고, rebase 한 번에 본문의
모든 참조가 죽는다. subject가 있으면 `git log --grep`으로 복구되고, 문자열이
`git log` 출력과 그대로 일치해 검색이 걸린다.

squash merge를 하지 않는 레포면 머지 후에도 해시가 살아 있다. 나중에 `git log`에서 그 커밋을
만난 사람이 PR 본문의 해당 섹션으로 역추적한다. squash 하는 레포면 해시는 머지 즉시 전부 죽으므로
subject 만 남긴다.

| 대응 | 판정 |
|---|---|
| 커밋 1개 : 섹션 여럿 | 허용. 커밋을 열면 두 내용이 다 거기 있다 |
| 섹션 1개 : 커밋 여럿 | 금지. 그 섹션은 논리 단위가 아니다 |

force-push 후에는 본문의 해시를 갱신한다. 갱신 부담을 줄이려면 스택 하위 수정을
rebase 대신 head 위 추가 커밋으로 처리한다.

## 3. 스크린샷

- **트리거**: 사람이 보는 화면이 달라졌을 때.
- **렌더**: ASIS-TOBE 2열 표.
- **계약**: 3행 고정 - 헤더 / 이미지 / 캡션.

```markdown
| ASIS (`<base>`) | TOBE (이 브랜치) |
|---|---|
| <img width="480" alt="ASIS - {무엇이 잘못 보이는지}" src="..." /> | <img width="480" alt="TOBE - {무엇이 보이는지}" src="..." /> |
| {지금 상태와 그것이 왜 문제인지} | {달라진 것} |
```

스크린샷을 본문에 흩뿌리지 않는다. 리뷰어가 무엇과 무엇을 비교해야 하는지를 표가 대신 말한다.

- `alt`에도 설명을 넣는다. 이미지가 안 뜨거나 스크린리더로 읽을 때 유일한 정보다
- 캡션은 각 1~2문장. 화면에 보이는 것을 나열하지 말고 **판정**을 쓴다
  ("좌하단에 숫자열이 있다" 아님, "외부 서비스 내부 식별자가 그대로 노출된다")
- 표 앞에 촬영 조건을 한 줄 적는다. 같은 계정, 같은 화면, 같은 데이터인지
- 세로로 긴 화면이라 좌우 배치가 어그러지면 `width`를 낮추거나 상하 2행 표로 바꾼다.
  스크린샷을 표 밖으로 빼지는 않는다

## 4. 금지

- 다이어그램 규칙 재정의 (pr-diagram.md 소관)
- 변경 파일 목록 나열 (diff가 그 자리에 있다)
- 빈 섹션 - 해당 없는 섹션은 지운다
- 개인 트래커 식별자. 팀 참조는 GitHub `#N`과 팀이 정한 트래커 키뿐
