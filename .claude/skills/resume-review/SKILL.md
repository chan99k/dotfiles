# 이력서 검토

## Overview

기술이사(서류 검토자) 관점의 이력서 기준. 핵심 전제 하나: **검토자는 이력서를 끝까지 읽지 않는다.**
위에서 아래로 훑다가 흥미가 끊기면 멈춘다. 그래서 이력서는 "빠짐없이 적는 문서"가 아니라
**위쪽 절반에서 승부가 나는 문서**다.

## When to Use

- 이력서 초안 작성 / 전면 재구성
- 특정 공고에 맞춘 변형본 제작
- 제출 직전 자가 점검
- 신입·경력 전환·레거시만 다룬 경력 등 "쓸 게 없다"는 상황

## 절대 금지 (하나라도 걸리면 다른 평가 무의미)

- **회사의 코드·기밀 사항 기재.** 사내 코드 스크린샷, MAU/동시접속자/CPU 사용률/API 응답시간
  같은 미공개 운영 수치, 장애 일시와 지속시간. 공개 배포 자료 범위를 벗어난 숫자는 전부 해당한다.
  → 지표가 필요하면 **본인 개인 프로젝트의 측정치**로 대체한다.
- 희망 연봉 기재
- 관리 안 된 GitHub·블로그 링크 (0 contributions, 마지막 글 몇 년 전)

## 구조 (이 순서를 지킨다)

```
[이름]
[연락처 + 어필할 외부 링크(블로그·GitHub)]        [프로필 사진]
[자기소개 3~5줄]

[경력 또는 프로젝트(신입)]
[회사명] [재직기간]
  [회사에 대한 간단한 설명]                    ← 검토자는 지원자의 회사·도메인을 모른다
  [어필할 주요 프로젝트명] (Option: 기간)
    [프로젝트 간단한 설명]
    [프로젝트 충분한 설명]

[오래된 회사명] [재직기간]
  - [주요 업무 1~2줄] × 3                      ← 과거로 갈수록 압축

[Option: 어필할 외부 활동]
[Option: 기술 스택 — 정말 자신 있을 때만]
[학력 및 수상]
```

- 최근 사항이 가장 위. 오래된 이력은 줄 수를 줄인다.
- 분량 3장 목표. 이력서에 **경력기술서를 통째로 넣지 않는다**(별도 문서).
- 2단 컬럼·아이콘·색상 디자인 금지. 시선이 분산된다.
- **외부 링크로 나가야만 이해되는 이력서를 만들지 않는다.** 링크는 보강이지 본문이 아니다.
- 기술 스택을 쓴다면 Backend·DevOps 정도로만 묶는다. 협업 도구(Jira·Notion·Trello)는 별도 섹션을 만들지 않는다.

## 흔한 실패 (스캔용)

| 증상 | 교정 |
|---|---|
| 누구나 쓰는 템플릿 그대로 | 구조는 위 형식, 내용은 본인 것 |
| 20줄짜리 불릿 나열 / 같은 내용을 장문 산문으로 | 읽히는 양까지만 남긴다 |
| 회사명·기간만 있고 업무 내용이 1~2줄 | 반대 극단. 무엇을 판단했는지가 없으면 읽을 게 없다 |
| 같은 동사(점검·확인·관리·검토) 반복 | 동사가 단조로우면 한 일도 단조롭게 읽힌다 |
| 모든 항목이 문제-해결-기술-성과 4단 반복 | 반복 형식은 피로감을 준다. 강한 항목만 상세히 |
| 기술명 볼드 남발 | 과대 포장으로 읽힌다 |
| 기술 스택에 상/중/하 표기 | 쓰지 않는다 |
| 초등학교부터 시작하는 자기소개 | 3줄로 끝낸다 |
| 이력 나열 | 스토리로 쓴다 — 왜 그 선택을 했는가 |

## 검토자의 시선 (제출 전 자가 점검)

- [ ] **N초 안에 첫인상이 결정된다** — 첫 화면에 무엇이 보이나
- [ ] **위에서 아래로 읽고, 다 읽지 않는다** — 아래쪽에만 있는 강점은 없는 것과 같다
- [ ] **최근 이력이 중요하다** — 오래된 것에 지면을 뺏기지 않았나
- [ ] **쇼츠와 같다** — 궁금증 → 기대 → 실망으로 꺾이는 지점이 어디인가
- [ ] **전체 지원자 기준으로 평가된다** — 나만 보면 괜찮은 게 아니라, 100장 중에서
- [ ] **회사와 도메인을 모른다** — 회사 한 줄 설명이 있나
- [ ] **척하면 들킨다** — 설명 못 할 기술이 적혀 있나
- [ ] **검토자는 한 줄 요약을 만든다** — 내 이력서의 한 줄 요약은 무엇인가

## 운영

- **원천 문서를 따로 둔다**: `RESUME_RAW.md`(전부 기록) → `RESUME_SPEC.md`(정제) → 제출본.
  제출본은 매번 여기서 파생시킨다.
- **최소 6개월마다 갱신.** 기억이 남아 있을 때 원천에 적는다.
- 지원 회사별 맞춤본을 만들고, **채용 공고의 어휘를 그대로 활용**한다.
- 자기소개와 본문의 톤을 통일한다.
- 이력서를 쓴 다음 **그 이력서로 받을 질문을 예상**한다. 답 못 할 항목은 지운다.

## 신입 / 특수 케이스

- 신입은 경력 자리에 프로젝트를 넣는다. 5개 질문에 답하며 채운다:
  무엇을 만들었나 / 왜 그렇게 만들었나 / 무엇이 막혔나 / 어떻게 풀었나 / 다시 하면 뭘 바꾸나
- 추가 노력: 블로그·SNS·개발 활동에서 **같은 프로필로 각인**되도록 통일
- 레거시 개선만 한 경력: "무엇을 유지했나"가 아니라 **무엇을 판단해서 바꿨고 무엇을 일부러 안 바꿨나**
- AI 활용 경험은 "AI를 썼다"가 아니라 **AI에 맡긴 범위와 사람이 판단한 범위의 구분**으로 쓴다

## 후속 — humanize-korean 윤문 (조건부)

이 스킬의 기본 산출물은 지적 코멘트다. 코멘트는 이력서 본문이 아니므로 윤문하지 않는다.
**이력서 문장을 실제로 새로 쓰거나 고쳐 준 경우에만** 그 결과에
`humanize-korean:humanize-korean` 스킬을 호출한다.

| 상황 | 윤문 |
|---|---|
| 체크리스트·지적만 반환 | 하지 않는다 |
| 자기소개 3~5줄 / 프로젝트 설명 문단을 새로 작성 | 한다 |
| 사용자가 "AI 티 나나", "문장 다듬어줘" 를 요청 | 한다 |

- **입력**: 다시 쓴 산문 단락만. 구조 스켈레톤, 불릿 목록, 회사명·기간·수치 줄은 제외한다.
  humanize는 리듬을 고르는 도구라 명사 나열 줄을 문장으로 풀어 늘일 수 있고,
  이력서에서 늘어난 분량은 그 자체로 감점이다.
- **route_hint**: `standard`. 등급 B 이하면 `heavy` 로 1회 재실행하고 거기서 멈춘다.
- **윤문 후 확인**: 수치·기간·고유명사가 그대로인가 / 줄 수가 늘지 않았나.
  어긋나면 해당 문장만 윤문 전으로 되돌린다.
- humanize는 내용을 더하지 못한다. **"무엇을 판단했는가"가 비어 있는 문장은
  윤문해도 비어 있다.** 그 공백은 위 체크리스트로 먼저 메운다.
