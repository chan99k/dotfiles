# Inspect — 변경 영향 분석

> **읽기 전용**. 이 스킬은 코드를 수정하지 않는다. 분석 리포트만 생성한다.

`$ARGUMENTS`가 주어지면 해당 작업(기능, 버그, 리팩터링)의 맥락으로 분석한다.

## 실행 순서

### Phase 1: 요구사항 이해

1. `$ARGUMENTS`에서 작업 목표를 파악한다
2. 관련 도메인 용어를 `docs/domain/*/language.yaml`에서 조회한다 (존재 시)
3. 관련 설계 문서를 `docs/plans/`, `docs/`, ADR 디렉터리 등에서 찾아 읽는다 (존재 시)

### Phase 2: 코드 탐색

1. **진입점 식별**: 작업과 관련된 파일을 Glob/Grep으로 찾는다
2. **의존 그래프 추적**: 해당 모듈/함수를 참조하는 모든 파일을 추적한다
   - 멀티모듈(도메인 분리): Controller → Service → Domain (Port) → Adapter 흐름 추적
   - 단일모듈: 패키지 경계(예: domain/service/repository) 기준으로 추적
3. **테스트 현황**: 관련 테스트 파일 존재 여부와 커버리지를 확인한다

### Phase 3: 변경 지점 식별

1. **직접 변경**: 수정이 필요한 파일 목록
2. **간접 영향**: 변경으로 인해 깨질 수 있는 코드
   - Entity 필드 변경 → DTO, Repository, Service, Controller
   - 뷰 템플릿(Thymeleaf/JSP/React 등)이 있으면 → model attribute/props 변경 영향
   - Port 인터페이스 변경(클린 아키텍처) → Adapter 구현체
   - 관련 테스트 파일
3. **DB 스키마 영향**: 필드 추가/변경 시 마이그레이션 필요 여부
4. **API 계약 영향**: OpenAPI spec / proto / 클라이언트 계약 변경이 필요한가?
5. **뷰 영향**: 서버 사이드 뷰 또는 프론트엔드 컴포넌트가 있는 경우 model 변경 영향

### Phase 4: 사이드이펙트 예측

1. **도메인 불변식 위반 가능성**: Entity 필드 변경이 도메인 규칙을 깨뜨리는가?
2. **의존성 순환**: 새 의존성이 레이어 방향 원칙을 위반하는가?
3. **API 호환성**: DTO/응답 변경이 클라이언트를 깨뜨리는가?
4. **뷰 정합성**: model attribute 변경이 템플릿/컴포넌트 렌더링을 깨뜨리는가? (뷰가 있는 경우)
5. **레이어 위반 가능성**: 변경이 아키텍처 의존성 규칙을 위반할 수 있는가?

### Phase 5: 아키텍처 규칙 점검

`.claude/rules/` 하위에 아키텍처 rule 파일이 있으면 그 기준을 우선 적용한다.
없으면 아래 일반 원칙을 적용한다:

1. 변경 대상 파일이 올바른 레이어/패키지에 위치하는가?
   - 멀티모듈: domain/application/ui/infrastructure 레이어 분리 원칙
   - 단일모듈: domain, service, repository, controller 패키지 역할 원칙
2. 의존성 방향이 올바른가? (도메인이 인프라를 직접 참조하면 위반)
3. Controller에 비즈니스 로직이 포함되지 않는가?
4. `@Transactional`이 서비스/유스케이스 레이어에 위치하는가?
5. 생성자 주입을 사용하는가? (필드 주입 금지)
