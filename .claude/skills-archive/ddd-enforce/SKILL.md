# DDD Enforce — 유비쿼터스 언어 준수 검증

> 구현 완료 후 또는 리뷰 시 실행하여 도메인 언어 준수를 검증한다.

`$ARGUMENTS`가 주어지면 해당 도메인/파일 범위로 검증한다.
없으면 전체 변경사항을 대상으로 검증한다.

## 참조 문서

- `docs/domain/*/language.yaml` — 도메인별 유비쿼터스 언어 정의 (존재 시)
- `.claude/rules/` 하위 rule 파일 — Backend 네이밍 규칙 (존재 시 우선 적용)

**language.yaml이 없는 경우**: 코드 네이밍 일관성만 검증한다.
패키지명, 클래스명, 메서드명이 동일 개념에 대해 일관된 용어를 사용하는지 확인한다.

**rule 파일이 없는 경우**: 인라인 일반 원칙을 적용한다 (네이밍 일관성, 인프라 관심사 누출 감지).

## 검증 절차

### Phase 1: 도메인 언어 로드

1. `docs/domain/` 하위의 모든 `language.yaml` 파일을 읽는다 (존재 시)
2. 각 도메인의 용어(terms), 금지 동의어(synonyms)를 수집한다
3. language.yaml이 없으면 코드에서 사용하는 주요 용어를 직접 추출한다

### Phase 2: 코드 검증

변경된 소스 파일을 대상으로:

1. **클래스명**: language.yaml의 용어와 일치하는가? (또는 코드 내 일관성)
   - Entity, Service, Controller, DTO 이름
2. **함수명/변수명**: 도메인 용어를 정확히 사용하는가?
3. **패키지 구조**: base package 하위 패키지명이 도메인 개념과 일치하는가?

### Phase 3: 뷰/API 검증 (존재 시)

서버 사이드 뷰(Thymeleaf/JSP) 또는 API 엔드포인트가 있는 경우:

1. **URL 경로**: `@RequestMapping` path / REST 엔드포인트가 도메인 용어를 사용하는가?
   - 예: `/novels` (O), `/books` (X — 금지 동의어일 경우)
2. **model attribute / 응답 필드명**: 도메인 용어를 반영하는가?
3. **템플릿 파일명/디렉터리명**: 도메인 개념과 일치하는가? (서버 사이드 뷰인 경우)

### Phase 4: 인프라 관심사 누출 감지

도메인 로직에 인프라 구현 세부사항이 누출되었는지 검증한다:

1. **domain/ 패키지**: JPA/Spring 어노테이션이 과도하게 사용되는가?
   - `@Entity`, `@Id`는 허용 (옵션 A 사용 시)
   - `@Transactional`, `@Controller` 등은 domain에 위치하면 위반
2. **외부 프로토콜**: `HTTP`, `REST`, `GRPC`, `KAFKA` 등이 도메인 타입에 있는가?
3. **직렬화 형식**: `Json`, `Xml`, `Proto` 등이 도메인 타입에 있는가?

**판단 기준**: 도메인 로직은 "무엇을 하는가"(비즈니스 규칙)만 표현해야 한다.
"어떻게 하는가"(구현 기술)가 도메인 타입이나 함수에 드러나면 위반이다.

## 출력 형식

```markdown
## DDD Enforce Report

**검증 범위**: <파일 목록 또는 도메인명>
**참조한 language.yaml**: <파일 경로 목록 또는 "미도입">

### 위반 사항
| # | 파일:라인 | 현재 용어 | 올바른 용어 | 종류 |
|---|----------|----------|-----------|------|
| 1 | ... | ... | ... | 금지 동의어 / 미정의 용어 / 불일치 |

### 확인 완료
- 검증 통과한 도메인 용어 목록

### 권고
- language.yaml에 추가가 필요한 새 용어
- 금지 동의어 목록에 추가할 용어
```
